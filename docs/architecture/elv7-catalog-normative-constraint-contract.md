# ELV7 — Catalog Normative Constraint Contract

Status: normative design contract  
Branch: `feat/flutter-elv7-normative-validation-design`

## 1. Purpose

ELV7 SHALL decide whether an engineering solution or equipment candidate is compliant with the project's selected normative profile.

ELV7 does not own manufacturer catalog data and does not choose the cheapest/preferred SKU.

> Catalog facts are evidence. ELV7 rules decide whether those facts satisfy the selected normative profile.

## 2. Separation of facts and rules

The system SHALL keep four categories separate:

1. **manufacturer facts** — ratings, dimensions, declared characteristics, certificates;
2. **project requirements** — demand generated by ELV5 and project policy;
3. **physical evidence** — placement/thermal/routing evidence produced by ELV6;
4. **normative rules** — jurisdiction/profile-specific constraints evaluated by ELV7.

A product row MUST NOT contain a boolean such as `compliantKz=true` as authoritative truth.

## 3. Versioned rule packs

Every normative rule belongs to an immutable/versioned rule pack.

```text
NormativeProfile
  profileId
  jurisdiction
  edition
  effectiveFrom/effectiveTo
  rulePackVersion
  referencedDocuments[]
```

Projects SHALL pin the exact normative profile/rule-pack version used for qualification and deliverables.

Updating a global rule pack MUST NOT silently rewrite an existing project's compliance result.

## 4. Rule model

Rules SHALL be declarative where practical and evaluated by deterministic code.

```dart
final class NormativeRule {
  final String ruleId;
  final String domain;
  final RuleSeverity severity;
  final RuleScope scope;
  final RulePredicate predicate;
  final List<NormativeReference> references;
  final String remediationCode;
}
```

The rule representation MAY use an internal AST/DSL, but MUST NOT rely on arbitrary executable scripts from catalog imports.

## 5. Rule output and explainability

Every evaluation SHALL produce evidence sufficient for engineering review:

```text
ruleId
profileVersion
verdict = PASS | FAIL | WARNING | NOT_APPLICABLE | INDETERMINATE
subjectIds[]
observedFacts[]
requiredConstraint
normativeReference[]
assumptions[]
remediationHint
```

A simple `valid=false` result is prohibited for safety-relevant checks.

## 6. Candidate evaluation contract

ELV8 SHALL be able to ask ELV7 to evaluate a candidate/assembly without committing it.

```dart
abstract interface class NormativeCandidateEvaluator {
  CandidateCompliance evaluate({
    required EquipmentDemand demand,
    required CandidateAssembly candidate,
    required NormativeProfileRef profile,
    PhysicalEvidence? physicalEvidence,
  });
}
```

The call MUST be side-effect free.

## 7. Hard constraints vs engineering advisories

Rules SHALL explicitly classify outcomes:

- `BLOCKING` — candidate cannot be resolved/issued;
- `REQUIRES_ENGINEER_DECISION` — manual documented decision required;
- `WARNING` — allowed but surfaced;
- `INFORMATIONAL` — evidence only.

A ranking algorithm MUST NOT compensate for a `BLOCKING` violation with lower cost or higher availability.

## 8. Certification and evidence provenance

Catalog certification claims SHALL include, where available:

- scheme/standard identifier;
- certificate/declaration identifier;
- issuer/source;
- valid-from/valid-to;
- applicable product/variant;
- source document hash/reference;
- ingestion timestamp;
- verification state.

Missing evidence SHALL be distinguishable from explicit non-compliance.

## 9. Override policy

Manual overrides MUST be explicit and auditable:

```text
overrideId
ruleId
subjectId
reason
actor
createdAt
projectRevision
scope
```

Blocking life-safety rules MAY be configured as non-overridable by profile policy.

No UI action may silently suppress a failed normative rule.

## 10. Interaction with external power sources

Rules SHALL be capability-based so the same engine can qualify utility, generator, UPS, PV/inverter, battery storage and hybrid-source modes.

Rules may constrain, for example:

- source transfer/parallel operating mode;
- protective-device capabilities;
- isolation/disconnection requirements;
- source-dependent fault-current assumptions;
- backup/autonomy requirements;
- enclosure/environment requirements;
- documentation/evidence obligations.

The source type MUST NOT require a new rule-engine architecture.

## 11. No LLM authority

AI/LLM features MAY assist with ingestion, mapping or human-readable explanation, but SHALL NOT be the authoritative compliance engine.

The authoritative result MUST come from versioned deterministic rules and structured facts.

## 12. Acceptance criteria

1. manufacturer facts and normative rules are stored separately;
2. every safety-relevant verdict is traceable to rule ID, profile version, evidence and reference;
3. candidate evaluation is pure and can run before ELV8 commits a selection;
4. blocking violations cannot be traded off by ranking;
5. missing/unknown evidence produces `INDETERMINATE`, not a fabricated pass;
6. project rule-pack pinning guarantees deterministic replay;
7. overrides are explicit, scoped and audited;
8. alternative/hybrid power sources can be qualified through capabilities and operating modes;
9. rule tests include positive, negative, boundary and missing-evidence fixtures;
10. changes in a normative profile invalidate only dependent qualification results, not unrelated catalog facts.
